## PR A: searchable knowledge foundation

`catalog-products` is an authenticated Edge Function with two bounded operations. `search` accepts 2-80 visible characters and returns at most 20 canonical product summaries. `detail` accepts a catalog product UUID and optional variant UUID and returns identity, variant metadata, and only formula evidence that meets S6's verified provenance constraints. It returns no member-specific records or verdict. Internal source references stay in server-only database columns. Customer detail includes a source link only from a separate operator-approved `publicSourceUrl`; HTTPS on an internal source is never enough. Public URLs reject credentials and query strings. A service-only SQL search function ranks exact brand plus name, exact name or alias, prefix, then trigram similarity, followed by stable brand/name/UUID ordering. PostgreSQL B-tree prefix and `pg_trgm` indexes bound typeahead work. The mobile app never downloads the full catalog.

Variant source reference, observation date, and verification state are stored additively on S6 variants; these fields document package evidence without changing resolver trust rules. A new `product_search_aliases` table records a sourced alternate name for an existing canonical product. Customer roles receive no write grant. The existing product read policy is narrowed: authenticated members can read shared catalog products and provisional products linked to their own Shelf, but not another member's provisional products. Source reference, observation time, and verification time are retained for newly operator-confirmed product identities. An authenticated search reads only confirmed catalog rows. A trusted CLI ingestion path accepts a single product and optional aliases, variant, identifier, and formula information. It inserts through one transaction, validates source and S6 relationships, and allows product-only entries. A formula requires exact ingredients and a source. A verified formula requires S6-accepted provenance. GTIN authority and any formula linkage follow S6 rules; no payload field can create a member-facing personalized verdict.

A source-backed initial product may be added after deployment only if the founder confirms the choice. No variant, GTIN, or formula is inferred from a product page. Manufacturer pages can identify a product family but commonly warn that ingredients change by package and time.

## Stable catalog API

`POST /functions/v1/catalog-products` accepts an authenticated session. Search request: `{"operation":"search","query":"CeraVe","limit":10}`. Its response is `{items: CatalogProductSummary[]}` with canonical ID, brand, name, category, no image until public image provenance exists, active variant count, and a conservative formula-availability state. Empty or one-character queries return no results; valid requests are capped at 20. Search never returns provisional products or user-specific records. Ranking is exact brand plus name, exact product name, exact alias, prefix, substring, then indexed trigram word similarity. Equal matches sort by brand, product name, and UUID.

Detail request: `{"operation":"detail","productId":"<uuid>"}` with optional `variantId`. It returns one canonical product and up to 30 active variants. Formula facts appear only when an S6 verified formula has exactly one authoritative verified identifier link for the selected variant. Multiple linked versions produce `multiple_versions` with no ingredients rather than choosing a package formula. The Edge function returns no personalized fit and never calls a model.

## Operator workflow

The operator input is one JSON entry with `product` (`brand`, `name`, `category`, `sourceReference`, optional `publicSourceUrl`, `observedAt`), optional sourced `aliases`, and optional sourced `variant`, `formula`, and `identifier`. A product-only record is valid. A formula entry requires exact ordered ingredients, provenance, source, observation time, and verification state. The CLI derives S6's normalized fingerprint; verified formula status rejects member-photo-only provenance. GTIN type, length, and check digit must match; an authoritative verified identifier can link to the exact verified formula of the same variant. Replays reuse the product/alias/variant and matching append-only evidence without rewriting source history.

Run a read-only preview with Node 22: `node --experimental-strip-types scripts/catalog-ingest.mjs --file <entry.json> --project-ref snojlbqovlawewwqbviz`. To apply after reviewing the entry and the target project, add `--apply` and set `SUPABASE_CLI` to an authenticated Supabase CLI if it is not on `PATH`. The script sends hex-encoded JSON to the restricted `private.ingest_catalog_product` function through the management CLI, keeping arbitrary product text out of SQL syntax. For a disposable local test use `--local` instead of `--project-ref`. Customer roles cannot execute the ingestion function or write canonical aliases, variants, identifiers, or formula versions.

The approved first live entry is [`cerave-renewing-sa-cleanser.json`](catalog-seeds/cerave-renewing-sa-cleanser.json), sourced from [CeraVe's official product page](https://www.cerave.com/skincare/cleansers/renewing-sa-cleanser). Its alias helps search. It intentionally contains no package variant, GTIN, formula ingredients, or actives because the manufacturer warns that ingredient lists change and the customer's exact package is not known.

## Mobile consumer implementation

The onboarding Shelf now starts with a debounced authenticated catalog search. One tap adds the selected canonical UUID immediately with `isCatalogStandard = true` and empty chemistry. The search field clears for another selection. A separate `Can't find it? Add manually` path keeps the V1A provisional builder and allows continuation without a catalog match. Editing a catalog product into a different identity creates a new provisional manual entry instead of retaining the catalog UUID. Optional shelf photography remains available, but does not pretend that live visual recognition is active.

The existing `/shop/scan` route is the single Check a Product route. It starts with name search, offers barcode camera input, and sends typed/barcode evidence to S6 with caller UUIDs. Name and barcode results use the same canonical product ID. Ambiguous candidates can be retried with their exact typed label/variant, while unresolved evidence remains in founder review. The client service accepts the full S6 evidence contract, including label text, ingredient lists, and private evidence paths, for a later capture/provider milestone; it does not activate OCR or public image upload here.

Product detail separates **Personal Fit** from **Formula Details**. H1P is not active in this release, so personal fit is unavailable rather than guessed. Full ingredients appear only when the member's S6 case is `verified_product_formula` and its product, variant, and formula version match the catalog detail. Product-only entries, typed identity without package verification, and multiple formula versions show an honest unknown state. Ambiguous S6 results show candidates without opening a selected product detail. No numeric compatibility score is used.

**Routine identity handoff:** `propose-routine` reads the committed intake snapshot and validates any selected catalog UUID against the sourced product row and its brand, name, and category. It passes an opaque Shelf reference to the provider, never a product UUID. After both the original and bound proposals pass the existing safety validator, the server resolves that reference back to the validated ID and supplies it to the existing atomic routine RPC for both steps and user products. A reference that conflicts with another known product fails closed. Manual/provisional entries retain the name-based fallback. This binds product identity only; no variant or formula is inferred. The controlled local fixture deliberately changes selected product wording to verify that the persisted and member-read IDs remain canonical without activating H1P.

A disposable hosted account proved real committed intake, controlled provider-free binding and routine persistence, and authenticated member readback against the approved sourced CeraVe product. Exact IDs matched; the account, routine, and private photos were then removed and read back as absent. Hosted `propose-routine` itself cannot complete a live proposal without the separate H1P provider decision, so this smoke proves the deterministic identity and persistence path rather than provider availability.

Current Remote Staging keeps Ask and Check a Product hidden, including direct `/shop/scan` routes. The old `PROTOTYPE_CATALOG` remains reachable only through developer/mock test shortcuts, not customer name search or barcode authority. This PR does not create a TestFlight build or activate provider-backed fit.
