# OTC sunscreen label candidates: inactive server-side adapter

Status: implemented as an isolated, **default-OFF** server-side module on 2026-09-28. It is not composed into Check, deployed, or enabled for customers. This is candidate label evidence, not a product database or a verified formula path.

## Exact input and output boundary

`lookupOtcSunscreenLabelCandidates` accepts either an exact, user-supplied brand name or a **segmented NDC explicitly obtained as an NDC**. It rejects an undashed numeric UPC/GTIN and does not guess UPC↔NDC mappings. The openFDA Drug Label endpoint is queried with an exact field and at most three results. Returned records are screened again for the exact supplied value, `HUMAN OTC DRUG`, and a sunscreen claim. Multiple or truncated results stay candidates, not a selected product. The adapter makes at most one openFDA call and, only for a single non-truncated candidate, one DailyMed v2 `/spls.json?setid=...` metadata cross-check.

Each candidate carries the openFDA record ID, SPL set ID, label effective date, separate **raw** active-ingredient and inactive-ingredient label-text arrays, brand/NDC assertions, fetch time and a source URL. DailyMed's SPL version and publication date are attached only when the returned set ID matches. The raw text is not parsed into an INCI formula: openFDA's active-ingredient field can contain a combined “Active ingredients Purpose” paragraph, and inactive-ingredient text can include non-ingredient wording. Neither FDA nor NLM verifies submitted label contents for this use. A DailyMed set ID/version corroborates a label record, not the customer's exact physical package or current formulation.

The module has no database writes, Auth bypass, client import, resolver composition or personal verdict. It requires `enabled: true` **and** a server-only openFDA API key to call the network; otherwise it returns a typed disabled/configuration outcome. The blank `OPENFDA_API_KEY=` slot is in `supabase/.env.example`; it belongs only in ignored local Edge secrets or the hosted Supabase secret store **after** review, never in root Expo `.env.local`, a mobile bundle, GitHub, or a chat message. Merely setting the secret does not activate this adapter. One bounded response reader (512 KiB), three-result cap, at-most-two calls and a timeout of at most five seconds fail closed on errors. The key is sent through the officially documented Basic-auth method and never returned in a result. Do not log raw user inputs or label text. Production composition still needs an explicit privacy/traffic review, quota/circuit-breaker budget, product-truth handoff and physical-package acceptance tests.

## Rights and use gate

The [openFDA terms](https://open.fda.gov/terms/) describe most data as public-domain/CC0 but caution that some submitted third-party works may retain copyright. They provide no accuracy warranty. The [Drug Label endpoint](https://open.fda.gov/apis/drug/label/) says the information is submitted by companies and **not verified by FDA**, may differ from the currently distributed package, and must not be relied on for medical-care decisions. The [current authentication page](https://open.fda.gov/apis/authentication/) says an API key is required and lists 240 calls/minute and 120,000/day per key. Those platform ceilings are not an application budget or permission to bulk harvest. The [DailyMed v2 service](https://dailymed.nlm.nih.gov/dailymed/app-support-web-services.cfm) supports current SPL metadata; its [set-ID filter](https://dailymed.nlm.nih.gov/dailymed/webservices-help/v2/spls_api.cfm) provides version/publication metadata. [NLM's disclaimer](https://dailymed.nlm.nih.gov/dailymed/about-dailymed.cfm) says DailyMed labeling may differ from FDA-approved or distributed labeling and NLM does not review SPL content before publishing. No DailyMed throughput promise is assumed.

For launch, keep these records as transient candidate evidence unless source-content rights and retention are reviewed. Do not display FDA/NLM as endorsing Derive. Do not treat a label's NDC or ingredients as a verified GTIN-to-package formula. Only independently supported S6/ProductTruthSnapshotV1 evidence can promote canonical identity/formula truth; unsupported or conflicting cases stay unknown.

## Validation evidence

- The focused fixture tests cover default-off/no network, UPC-as-NDC rejection, server-key requirement, exact brand and NDC queries, active/inactive field separation, SPL cross-check, false-positive abstention, truncation, 404, provider error and oversized response.
- A read-only manual API probe on 2026-09-28 found one openFDA sunscreen record with distinct raw active/inactive fields and the same set ID in DailyMed v2, demonstrating endpoint shape only. It did **not** establish package match, catalog coverage, customer safety, or hosted behavior. No API key or third-party photo was stored in the repository.
