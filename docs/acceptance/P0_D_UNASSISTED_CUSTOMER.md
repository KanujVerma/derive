# P0-D unassisted first-value customer kit

**Status: PREPARED, NOT RUN.** Kanuj owns the release outcome. This extends the [P0-B comprehension protocol](P0_B_HUMAN_STUDY.md) to the whole scanner-first journey; it does not replace P0-B's decision-case record or count a fixture, founder, agent, or guided session as customer proof. The candidate audience is still an open release decision. An eligible U.S. adult unrelated to the team can test the initial journey without resolving any later teen policy; a teen study needs separate consent/privacy review.

## Prepare without coaching

- Use the exact intended build and hosted environment. Record source SHA, bundle ID, marketing version, native build number, distribution path, device/iOS, backend host, date and whether this is the final candidate. A local development session is useful feedback but does not clear TestFlight or public-release acceptance.
- Bring one real, independently identified product with a readable name and barcode; one real product absent from the catalog if available; a readable ingredient panel; and one difficult photo situation such as glare, curvature or small text. Do not manufacture a formula assertion from packaging. Check the expected known/unknown identity state before the session, privately.
- Use a disposable account or approved sample context. Do not collect a participant's actual photos, diagnoses, prescriptions, reproductive details, contact details, credentials or private skin history. Record only an anonymous session code, eligibility/consent yes/no, actions and paraphrased observations. Do not screen-record by default.
- Keep the operator silent during the task. If the participant asks for help or cannot continue, record the exact screen, action and elapsed time; mark the affected attempt **assisted**. Help may be provided after recording that result for product feedback, but cannot turn it into an unassisted pass.

## Exact opening and tasks

Say: “We are testing whether Derive helps someone check a skincare product. This is a test of the app, not of you. You may stop at any time. We will take brief notes without your name or sensitive skincare details.”

Then say: “Use Derive to check this product and decide what you would do next.” Hand over the known product. Do not point to the camera, name search, account control, or optional personalization. Observe the first action, hesitation, unexpected route, permission response, recovery, result and time to a useful answer.

After that attempt, say: “Try checking this other product.” Hand over the preselected unknown product. Observe whether the app states uncertainty and whether the participant can recover through search, barcode or other available steps. If the candidate does not support ingredient or photo extraction, do not instruct the participant to expect it; record whether the interface itself created that expectation. The difficult package is a follow-up usability case only if the candidate exposes package capture.

Where the candidate offers optional personalization and My Stuff, say: “If you want to make this answer more personal, try that. Then find this check again.” Do not direct navigation. If the candidate lacks either capability, mark it **not exposed** and reconcile the listing instead of creating a false failure.

## Ask after use

Ask each once, without teaching between questions:

1. “What does Derive recommend?”
2. “Why?”
3. “Did anything about your current routine matter?”
4. “What is Derive uncertain about?”
5. “What should you do next?”

Accept accurate paraphrases. “No routine change was suggested” can be correct. If the result was factual-only, the participant should not have to invent a personal recommendation. Do not turn a useful unknown into a claimed verified product or formula. The [P0-B protocol](P0_B_HUMAN_STUDY.md) defines the deeper per-decision scoring; this kit additionally records first value and recovery.

## Minimal observation record

Copy this blank record for each candidate run. No row is pre-passed.

| Field | Record |
| --- | --- |
| Anonymous session, eligibility, consent | Not run |
| Candidate source/build/environment/device/date | Not run |
| Known and unknown case IDs, independently known facts | Not run |
| First action and time to useful result | Not run |
| Camera/name-search choice and permission behavior | Not run |
| Hesitation, wrong route, help request, recovery | Not run |
| Supported fact versus personal guidance understood | Not run |
| Recommendation, reason, routine effect, uncertainty, next step | Not run |
| Unknown-product recovery and any false certainty | Not run |
| Optional personalization and explicit save/revisit, if exposed | Not run |
| Actual limitation the participant inferred | Not run |
| Assisted, interrupted or unassisted outcome | Not run |
| Release-blocking defect and owner, if any | Not run |

Mark each of the five answers **understood**, **partly understood**, **misunderstood**, or **not observed** against the actual bound result. A case passes only when the participant reaches a useful next step without assistance and understands all material meanings, including uncertainty and caution. Do not average away a mistaken safety claim or false product certainty. Retain failed observations after a fix and run a fresh session; no human gate is cleared until an eligible person actually completes it on the intended candidate.
