## Initial profile

Check opens before optional profile. Four screens collect the same five topics: goals; usual skin feel **and** reactivity; current products; past reactions. Feel/reactivity share one screen because they are two related short questions; neither input was removed. The actual Expo Go screenshot shows both groups and Continue/Back together. This is a grouping choice, not a new decision rule. Spending/strength editors remain contextual preferences, outside fresh onboarding. Reactions appear after selecting an actual catalog product or explicitly confirming a manually named, unverified product. Membership in a routine is not reported helpfulness, and adverse product experience is not ingredient causation.

The approved local setup draft is a separate `@derive/setup-draft/v1` AsyncStorage record. It stores existing goals/skin feel/reactivity, selected current/past products and their existing feedback/use facts, step0–3, owner/session generation, base context revision and timestamps. It excludes search text, notes, medical/reproductive answers, photos and secrets. It is capped at64KiB, expires seven days after the last edit, debounces500ms and flushes on background/unmount. Completion, sign-out, owner/session change and account deletion clear it. Restoration requires the same authenticated owner/session and context revision; invalid/expired records are discarded on read. App storage is sandboxed, without additional application encryption; Expo Go's container differs from the standalone binary. Expiry is enforced on access, not a promise of wall-clock deletion while the app is stopped. The Part3 metadata-only Save recovery contract is unchanged.

Foreground access refresh keeps the established owner's navigation mounted while revalidating, rejects stale/foreign acknowledgments and fails closed on error. This does not bypass backend authorization.
